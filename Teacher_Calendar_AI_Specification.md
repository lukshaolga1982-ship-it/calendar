# Teacher Calendar — подробная инструкция для ИИ-разработчика

## 1. Роль ИИ и цель проекта

Ты — senior full-stack разработчик, UX/UI-дизайнер и специалист по календарным системам. Создай современное адаптивное веб-приложение **Teacher Calendar** — личный календарь преподавателя с облачной синхронизацией, повторяющимися уроками, учётом оплаты, посещаемости и часовых поясов.

Приложение должно напоминать Google Calendar по понятности взаимодействия, но быть специализированным под частного преподавателя. Основной пользователь — один преподаватель. Доступ к данным возможен только после авторизации.

Интерфейс приложения — на русском языке. Код, названия переменных, коллекций и технические комментарии — на английском языке.

## 2. Подтверждённые требования пользователя

- Только один владелец календаря, вход по аккаунту и облачная синхронизация между устройствами.
- Основной экран должен показывать **все дни выбранного месяца**.
- Должны быть представления: **Месяц**, **Неделя**, **Ближайшие**.
- Переключение месяцев кнопками назад/вперёд и быстрый возврат к сегодняшней дате.
- Создание одиночных и еженедельно повторяющихся уроков.
- Повторение по выбранным дням недели до заданной даты.
- Для серии доступны действия: изменить/удалить **только этот урок**, **этот и следующие**, **всю серию**.
- Урок содержит ученика или группу, предмет, дату, время, длительность, цвет, заметки, ссылку, стоимость, оплату, посещаемость и напоминания.
- Для каждого ученика или группы можно создавать домашние задания, привязывать их к уроку и отслеживать выполнение.
- Урок можно перенести, отменить, отметить проведённым или пропущенным.
- Одновременно показываются текущее время выбранного часового пояса и время по Москве.
- Около текущего времени находятся кнопки `−` и `+` для изменения выбранного часового пояса. После смены зоны **все уроки отображаются в пересчитанном времени**.
- Визуальная тема — женственная, современная и мягкая, но календарь должен оставаться рабочим и хорошо читаемым.

## 3. Что было изучено перед проектированием

Приложенное изображение используется как референс структуры месячного календаря:

- месяц целиком помещается в сетку из 7 колонок;
- в каждой ячейке видны номер дня и компактные цветные события;
- если события не помещаются, появляется строка «ещё N»;
- текущая дата выделена;
- навигация и создание события доступны прямо с главного экрана.

Не копируй старую визуальную стилистику изображения. Возьми только информационную плотность и структуру.

Полезные проверенные паттерны:

- Google Calendar поддерживает повторяющиеся события и изменение повторов: [Google Calendar Help](https://support.google.com/calendar/answer/37115?co=GENIE.Platform%3DDesktop&hl=en-GB).
- При работе с часовыми поясами календарь должен хранить исходную зону события и пересчитывать показ: [Google Calendar Help — time zones](https://support.google.com/calendar/answer/37064?co=GENIE.Platform%3DAndroid&hl=en-ch).
- Для сложных повторений можно использовать RRule: [FullCalendar RRule plugin](https://fullcalendar.io/docs/rrule-plugin).
- FullCalendar предоставляет month, time-grid, list, now-indicator, drag-and-drop и touch-инструменты: [FullCalendar documentation](https://fullcalendar.io/docs).

## 4. Рекомендуемый технологический стек

Используй:

- React + TypeScript + Vite;
- FullCalendar для сеток `dayGridMonth`, `timeGridWeek` и `list`;
- Firebase Authentication для входа;
- Cloud Firestore для облачных данных и синхронизации в реальном времени;
- Firebase Cloud Functions + Firebase Cloud Messaging для серверных напоминаний;
- `rrule` для повторяющихся событий;
- Luxon или Temporal API/polyfill для безопасной работы с IANA time zones;
- CSS Modules или обычный структурированный CSS с CSS custom properties;
- Lucide Icons для единообразных интерфейсных иконок;
- Zod для проверки форм и данных.

Не хранить основную базу уроков только в `localStorage`. Разрешается использовать локальное хранилище только для несекретных UI-настроек и кэша. Источник истины — Firestore.

## 5. Авторизация и безопасность

### 5.1 Вход

Реализуй:

- вход через Google;
- резервный вход через email/password;
- выход из аккаунта;
- восстановление пароля;
- экран загрузки, пока проверяется auth state;
- понятные сообщения об ошибках на русском языке.

### 5.2 Изоляция данных

Каждый документ пользователя должен содержать `ownerId`. Firestore Security Rules обязаны разрешать чтение и запись только когда:

```text
request.auth != null && request.auth.uid == resource.data.ownerId
```

Для создания дополнительно проверять, что `request.resource.data.ownerId == request.auth.uid`.

Никогда не размещай Firebase Admin credentials или приватные ключи во frontend-коде. Firebase web config допустим на клиенте, безопасность обеспечивается Authentication и Security Rules.

## 6. Информационная архитектура

### 6.1 Основной layout на компьютере

Верхняя панель:

1. логотип/название `Teacher Calendar`;
2. кнопка `Сегодня`;
3. стрелки предыдущего/следующего периода;
4. название выбранного месяца и года;
5. переключатель `Месяц / Неделя / Ближайшие`;
6. блок времени;
7. аватар и меню аккаунта.

Левая компактная панель:

- кнопка `+ Новый урок`;
- мини-календарь;
- фильтры учеников/групп;
- легенда статусов;
- кнопка настроек.

Центр:

- активное календарное представление;
- без горизонтального скролла в месячном режиме на desktop;
- сетка месяца занимает максимально возможную высоту окна.

### 6.2 Мобильная версия

- верхняя панель упрощается;
- переключение месяца — стрелками и горизонтальным свайпом;
- месяц остаётся доступен, но карточки уроков могут показывать только время, короткое имя и цвет;
- нажатие на день открывает bottom sheet со всеми уроками;
- отдельная плавающая кнопка `+`;
- недельный вид по умолчанию может показывать 3 дня с горизонтальной прокруткой, но пользователь всегда может выбрать полные 7 дней;
- все зоны нажатия — не меньше 44×44 px.

## 7. Представления календаря

### 7.1 Месяц

- Неделя начинается с понедельника.
- Показывать 5 или 6 полных недель так, чтобы были видны все дни месяца.
- Дни соседних месяцев видны приглушёнными.
- Сегодня выделено мягким круглым акцентом.
- В карточке урока: локальное время, короткое имя ученика/группы, иконка/точка статуса.
- Показывать максимум событий, который реально помещается в ячейке; далее `Ещё N`.
- Нажатие на `Ещё N` открывает popover или bottom sheet, не уводя пользователя с месяца.
- Нажатие на свободную область дня создаёт урок с предзаполненной датой.

### 7.2 Неделя

- Колонки дней и вертикальная шкала времени.
- Индикатор текущего времени.
- Рабочий диапазон по умолчанию 07:00–23:00, настраиваемый.
- Клик/drag по пустому интервалу создаёт урок.
- Drag-and-drop переносит урок.
- Изменение высоты карточки меняет длительность.
- Перед сохранением переноса повторяющегося урока спросить область применения.
- Конфликтующие уроки показывать рядом, а не накладывать нечитаемо.

### 7.3 Ближайшие

- Хронологический список на следующие 30 дней.
- Группировка по датам: `Сегодня`, `Завтра`, затем дата.
- Быстрые действия: открыть ссылку, отметить проведённым, оплату, отменить, перенести.
- Фильтры по ученику, группе, предмету, оплате и статусу занятия.

### 7.4 Домашние задания

Добавить отдельное представление `Домашние задания`, доступное из главной навигации. Оно не заменяет календарь, а дополняет его.

Предусмотреть два режима:

- `По сроку` — задания группируются в разделы `Просрочено`, `Сегодня`, `Завтра`, `На этой неделе`, `Позже`, `Без срока`;
- `По ученикам` — список учеников и групп с количеством активных, выполненных и просроченных заданий.

В верхней части показать компактную сводку:

- сколько заданий нужно проверить;
- сколько просрочено;
- сколько заданий должно быть выполнено сегодня;
- сколько выполнено за выбранный период.

На карточке задания показывать ученика/группу, краткий текст, предмет, дедлайн, статус и связь с уроком. Нажатие открывает полные детали. Должны работать поиск и фильтры по ученику, предмету, статусу и сроку.

## 8. Блок текущего времени и часовые пояса

### 8.1 Вид блока

Пример:

```text
Ваше время     18:42  UTC+02  [−] [+]
Москва         19:42  MSK · UTC+03
```

Дополнительно:

- показывать дату, если в Москве уже другой день;
- обновлять часы каждую минуту без перезагрузки;
- tooltip кнопок: `Сдвинуть часовой пояс на 1 час назад/вперёд`;
- по нажатию на название зоны открывать полноценный селектор IANA-зон с поиском по городу;
- кнопка `Определить автоматически`;
- Москва всегда рассчитывается как `Europe/Moscow`, а не как вручную заданный `UTC+3`.

### 8.2 Важное правило хранения времени

Хранить для урока:

- абсолютный момент начала в UTC;
- абсолютный момент окончания в UTC;
- IANA-зону, в которой урок был создан, например `Europe/Warsaw`;
- локальные компоненты исходного времени, если они нужны для генерации повторов.

При смене **зоны отображения** не менять UTC timestamps в базе. Менять только визуальное представление. Например урок в 18:00 Europe/Warsaw должен автоматически показываться в соответствующее время выбранной зоны.

Не прибавлять и не вычитать часы вручную. Использовать библиотеку зон и учитывать DST. В интерфейсе предупреждать, если сезонный переход изменит разницу с Москвой.

### 8.3 Семантика повторяющегося урока

Повторяющаяся серия должна быть привязана к локальному времени исходной зоны. Если занятие задано на 18:00 Europe/Warsaw, после перехода на летнее время оно остаётся в 18:00 по Варшаве, хотя его UTC-момент изменится.

## 9. Создание и редактирование урока

Форма открывается в правой панели на desktop и в полноэкранном sheet на mobile.

### 9.1 Обязательные поля

- `Ученик или группа` — выбор существующего или быстрое создание нового;
- `Предмет`;
- `Дата`;
- `Время начала`;
- `Длительность` — быстрые варианты 30, 45, 60, 90, 120 минут + произвольное;
- `Часовой пояс события`;
- `Цвет`.

### 9.2 Дополнительные поля

- ссылка на онлайн-урок;
- заметки;
- стоимость;
- валюта;
- статус оплаты;
- посещаемость/результат урока;
- напоминания;
- повторение.
- домашнее задание по итогам урока.

### 9.3 Умные значения по умолчанию

- последний использованный предмет;
- стандартная длительность из профиля ученика;
- цена и валюта из профиля ученика/группы;
- цвет ученика;
- основная зона пользователя;
- напоминание за 15 минут.

### 9.4 Валидация

- конец позже начала;
- цена неотрицательная;
- корректный URL с протоколом `https://`;
- дата окончания серии не раньше первого урока;
- выбран хотя бы один день повторения;
- при конфликте времени показать предупреждение, но разрешить сохранить после подтверждения.

## 10. Повторяющиеся уроки

### 10.1 Настройка серии

В форме есть переключатель `Повторять`.

После включения:

- частота: еженедельно;
- интервал: каждую 1, 2, 3 или 4 недели;
- дни: Пн, Вт, Ср, Чт, Пт, Сб, Вс — мультивыбор;
- окончание: обязательная дата `Повторять до` включительно;
- предварительный текст: `Каждую неделю по понедельникам и средам до 30 июня 2027`;
- показать количество будущих занятий до сохранения.

Хранить правило в стандартизированном виде RRule, например:

```text
FREQ=WEEKLY;INTERVAL=1;BYDAY=MO,WE;UNTIL=20270630T215959Z
```

Граница `UNTIL` должна вычисляться корректно в зоне серии. Нельзя терять последнее занятие из-за неверного преобразования полуночи в UTC.

### 10.2 Область изменения серии

При редактировании экземпляра серии всегда показывать диалог:

```text
К каким урокам применить изменения?
○ Только к этому уроку
○ К этому и всем следующим
○ Ко всей серии
[Отмена] [Продолжить]
```

Поведение:

- **Только этот урок**: создать exception/override для конкретного occurrence; исходную серию не менять.
- **Этот и следующие**: завершить старую серию непосредственно перед выбранным occurrence и создать новую серию с изменёнными параметрами начиная с выбранного occurrence.
- **Вся серия**: изменить master series; существующие индивидуальные исключения не удалять без отдельного предупреждения.

### 10.3 Удаление

При удалении повторяющегося урока использовать такой же выбор области:

- **Только этот урок**: добавить occurrence key в список исключённых дат/создать deleted exception.
- **Этот и следующие**: укоротить правило старой серии; не удалять прошедшие уроки и их финансовую историю.
- **Всю серию**: по умолчанию мягкое удаление серии; показать предупреждение о количестве будущих уроков. Сохранить историю проведённых занятий и оплат.

Удаление одного урока никогда не должно случайно удалять master series.

## 11. Перенос, отмена и посещаемость

Разделить понятия:

- `Запланирован` — обычное будущее занятие;
- `Перенесён` — occurrence получил новые дату/время; хранить исходные дату/время для истории;
- `Отменён преподавателем`;
- `Отменён учеником`;
- `Проведён`;
- `Пропущен учеником`;
- `Пропущен преподавателем`.

Отмена — не физическое удаление. Отменённый урок остаётся в истории, визуально приглушается и зачёркивается. Пользователь может указать, должен ли он быть оплачен.

Быстрое действие `Перенести` открывает выбор новой даты/времени. Для серии сначала спрашивать область применения.

## 12. Оплата и стоимость

### 12.1 Поля

- `priceAmount`;
- `currency`, по умолчанию из настроек;
- `paymentStatus`: `unpaid`, `paid`, `partiallyPaid`, `notRequired`, `refunded`;
- `paidAmount`;
- `paidAt`;
- необязательная заметка об оплате.

### 12.2 Отображение

Не полагаться только на цвет — использовать иконку/маркер:

- пустой кружок — не оплачено;
- половина кружка — частично;
- галочка — оплачено;
- перечёркнутый знак — оплата не требуется;
- обратная стрелка — возврат.

В карточке урока не перегружать месячный вид стоимостью. Полная финансовая информация видна в popover и списке ближайших.

### 12.3 Быстрая отметка оплаты

У каждого конкретного урока должна быть кнопка/checkbox `Оплачено`. Она доступна:

- в popover урока в месячном календаре;
- на карточке недельного вида;
- в списке ближайших уроков;
- в окне просмотра урока.

При нажатии:

- статус становится `paid`;
- автоматически записываются полная стоимость как `paidAmount` и текущее время как `paidAt`;
- появляется toast `Урок отмечен как оплаченный` с кнопкой `Отменить`;
- повторное открытие приложения сохраняет отметку в облаке.

Для нестандартной ситуации открыть расширенное меню оплаты: `Оплачено полностью`, `Оплачено частично`, `Не оплачено`, `Оплата не требуется`, `Возврат`. При частичной оплате запросить сумму. Разрешить исправить ошибочно указанную оплату.

Оплата всегда относится к конкретному occurrence, а не автоматически ко всей повторяющейся серии. Изменение цены для `этого и следующих` меняет ожидаемую стоимость будущих уроков, но не меняет уже записанные оплаты прошлых занятий.

### 12.4 Задолженности

Добавить фильтр/раздел `Не оплачено`, где показываются прошедшие проведённые уроки со статусами `unpaid` и `partiallyPaid`. В сводке отображать:

- общую сумму задолженности по каждой валюте отдельно;
- ученика/группу;
- дату урока;
- ожидаемую сумму;
- уже оплаченную сумму;
- остаток.

Не складывать разные валюты в одну некорректную сумму. Отменённые уроки попадают в задолженность только если для них явно включено `Подлежит оплате`.

## 13. Напоминания

Поддержать одно или несколько напоминаний:

- за 5, 10, 15, 30 минут;
- за 1, 2, 24 часа;
- пользовательский интервал.

Для браузерных push-уведомлений:

- запросить разрешение только после понятного объяснения пользы;
- хранить FCM token пользователя;
- планировать уведомления серверно;
- после переноса/отмены/изменения серии отменять старые задачи и создавать новые;
- не отправлять напоминание для удалённого или отменённого урока;
- при невозможности push показывать fallback внутри приложения.

Важно: service worker сам по себе не гарантирует точное уведомление в закрытом браузере. Для надёжности нужна серверная функция/очередь.

## 14. Ученики и группы

Создай справочник `Ученики и группы`.

Карточка содержит:

- тип: ученик или группа;
- имя/название;
- цвет;
- предмет;
- часовой пояс ученика/группы;
- стандартную длительность;
- стандартную цену и валюту;
- ссылку на урок;
- заметки;
- active/archive status.

При выборе ученика значения автоматически подставляются в урок, но могут быть переопределены только для конкретного урока.

В карточке ученика/группы добавить вкладку `Домашние задания`, где видны:

- активные задания;
- просроченные;
- ожидающие проверки;
- выполненные с датой выполнения;
- архив заданий;
- процент выполнения без агрессивной геймификации или публичного сравнения учеников.

## 15. Домашние задания

### 15.1 Создание задания

Домашнее задание можно создать:

- прямо из карточки проведённого или будущего урока;
- из профиля ученика/группы;
- из отдельного раздела `Домашние задания`;
- быстрым действием после отметки урока как проведённого.

После завершения урока ненавязчиво предложить: `Добавить домашнее задание?`. Не открывать форму принудительно.

### 15.2 Поля задания

Обязательные:

- ученик или группа;
- название или короткая формулировка задания;
- предмет.

Дополнительные:

- подробное описание с переносами строк и списками;
- дата и время выдачи;
- дедлайн;
- связь с уроком, после которого задание выдано;
- связь со следующим уроком, к которому нужно выполнить задание;
- ссылки на материалы;
- прикреплённые файлы;
- комментарий преподавателя;
- статус;
- приоритет;
- оценка или результат проверки;
- дата выполнения;
- дата проверки.

### 15.3 Статусы

Использовать отдельные статусы:

- `Черновик`;
- `Задано`;
- `Выполняется`;
- `Сдано / нужно проверить`;
- `Выполнено`;
- `Нужна доработка`;
- `Не выполнено`;
- `Отменено`.

Статус `Просрочено` лучше вычислять автоматически, а не хранить отдельно: дедлайн прошёл, а задание не находится в финальном статусе.

Поскольку на первом этапе календарём пользуется только преподаватель, он меняет статусы вручную. Архитектуру данных сделать расширяемой, чтобы позднее можно было предоставить ученику ссылку или личный кабинет без переделки всей модели.

### 15.4 Быстрые действия

- отметить выполненным;
- отметить сданным и ожидающим проверки;
- отправить на доработку;
- изменить дедлайн;
- дублировать для другого ученика или группы;
- открыть связанный урок;
- архивировать;
- удалить.

Удаление связанного урока не должно автоматически удалять домашнее задание. Связь становится пустой, но само задание и его история сохраняются. При удалении ученика с заданиями предложить архивировать ученика вместо физического удаления.

### 15.5 Групповые задания

Задание, выданное группе, является одним шаблоном, но должно позволять при необходимости отслеживать результат каждого участника отдельно. Для первого релиза допустим общий статус группы, однако модель данных должна поддерживать `assigneeProgress` по каждому ученику.

### 15.6 Файлы и ссылки

- Файлы хранить в Firebase Storage, а в Firestore — только метаданные и путь.
- Разрешить PDF, DOCX, изображения и другие безопасные учебные форматы.
- Ограничить размер одного файла и показывать прогресс загрузки.
- Проверять MIME type и расширение.
- Удаление задания должно удалять связанные файлы только после подтверждения и через безопасную серверную операцию.
- Ссылки валидировать и открывать в новой вкладке с безопасными атрибутами.

### 15.7 Напоминания о домашнем задании

Преподаватель может включить личное напоминание:

- проверить задание;
- напомнить себе о приближении дедлайна;
- проверить просроченные задания.

Не утверждать, что уведомление отправлено ученику: в текущей версии у ученика нет аккаунта и канала доставки. Возможность отправки ученикам является отдельной будущей функцией.

## 16. Поиск и фильтры

Реализуй:

- поиск по имени, группе, предмету и заметкам;
- фильтр по ученику/группе;
- фильтр по предмету;
- фильтр по статусу урока;
- фильтр по статусу оплаты;
- фильтр домашних заданий по дедлайну и статусу;
- кнопку `Сбросить`;
- активные фильтры в виде компактных chips.

Фильтры должны одинаково работать в месяце, неделе и ближайших уроках.

### 18.4 Почему нельзя хранить каждое будущее повторение заранее

Master + RRULE + exceptions предотвращают дублирование сотен документов и позволяют корректно изменить серию. Конкретные occurrences генерируются только для видимого диапазона календаря. Финансовые и статусные данные конкретного урока записываются в override.

Для быстрого запроса генерируй occurrences только между `visibleRangeStart` и `visibleRangeEnd`, затем применяй исключения. Не загружай всю историю при каждом открытии месяца.

## 19. Алгоритм формирования событий

1. Определить UTC-границы видимого диапазона с учётом выбранной зоны отображения.
2. Получить standalone events, пересекающие диапазон.
3. Получить активные series, которые потенциально пересекают диапазон.
4. Сгенерировать occurrences по RRULE в `sourceTimeZone` каждой серии.
5. Сформировать стабильный `occurrenceKey` из локальной даты и времени исходной зоны.
6. Применить deleted и modified overrides.
7. Преобразовать итоговые UTC-моменты в `displayTimeZone`.
8. Отсортировать и отрисовать.

Кэшировать вычисления по ключу `seriesId + updatedAt + range + displayTimeZone`.

## 20. Операции «этот и следующие»

Это критически важная транзакция:

1. Пользователь выбирает occurrence, с которого начинаются изменения.
2. В транзакции укоротить старый RRULE до occurrence непосредственно перед выбранным.
3. Создать новый series master с новым `dtStartLocal` и новыми параметрами.
4. Перенести/перепривязать overrides выбранного и будущих occurrences к новой серии, если они остаются логически совместимыми.
5. Не менять overrides прошедшей части.
6. Перепланировать будущие уведомления.
7. При любой ошибке откатить всю операцию.

## 21. Оптимистичные обновления и синхронизация

- После сохранения событие появляется сразу.
- При сетевой ошибке показать toast и вернуть предыдущее состояние.
- Firestore offline persistence разрешена как кэш.
- Показывать маленький статус `Синхронизировано / Сохраняется / Нет сети`.
- Не допускать повторного создания события при двойном клике.
- Использовать idempotency key для сложных операций серии.

## 28. Критерии приёмки

Приложение считается готовым, если:

- пользователь входит и видит свои данные на другом устройстве;
- весь месяц виден на одном экране desktop;
- месяцы переключаются без перезагрузки;
- работают месяц, неделя и ближайшие;
- серия создаётся по нескольким дням недели до даты;
- одиночный occurrence удаляется без удаления серии;
- работают `только этот`, `этот и следующие`, `вся серия`;
- перенос, отмена, посещаемость и оплата сохраняются;
- рядом показаны выбранное время и MSK;
- кнопки `−/+` меняют зону отображения, и календарь пересчитывается;
- смена зоны не повреждает исходные timestamps;
- DST покрыт тестами;
- напоминания обновляются после переноса/отмены;
- интерфейс адаптивный, доступный и визуально соответствует feminine theme;
- Firestore Rules не позволяют прочитать данные другого пользователя;
- домашнее задание создаётся из урока и профиля ученика;
- работают дедлайн, статусы, фильтры, архив и вложения;
- удаление урока не уничтожает связанное домашнее задание;
- нет критических ошибок в console.

## 30. Что не делать

- Не хранить всё расписание только в localStorage.
- Не генерировать заранее бесконечное число документов повторов.
- Не менять UTC timestamps при смене зоны **отображения**.
- Не хранить только числовой UTC offset вместо IANA time zone.
- Не удалять всю серию при удалении одного урока.
- Не удалять историю оплат и проведённых уроков при завершении серии.
- Не использовать системный `confirm()` в финальном UI.
- Не кодировать статусы исключительно цветом.
- Не перегружать месячные ячейки полной информацией.
- Не делать мобильную версию простым уменьшением desktop layout.
- Не хранить домашнее задание как неструктурированный текст внутри заметок урока.
- Не удалять домашнее задание автоматически вместе с уроком.
- Не обещать отправку задания ученику, пока у приложения нет ученического доступа или реального канала доставки.
